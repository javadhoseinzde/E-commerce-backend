1. INTEGRATION OVERVIEW
============================================================

Architecture:

    MenuNo SaaS
        |
        | HTTP POST (JSON body + HMAC headers)
        v
    MenuNo Core (Django + DRF)
        |
        | 1. CSRF exempt (server-to-server, no browser cookie)
        | 2. HMAC-SHA256 signature verification
        | 3. Timestamp freshness validation (5 min window)
        | 4. Event ID idempotency check
        | 5. Cafe lookup by external_id
        | 6. Plan sync (create or update)
        | 7. Subscription sync (create or update)
        | 8. Response returned
        v
    200/201 success

Data flow:
- SaaS is the SOURCE OF TRUTH for billing and subscription state.
- Core is the SOURCE OF TRUTH for cafe operational data.
- Core maintains a lightweight MIRROR of SaaS Plan and Subscription
  for access control (determining if a cafe has an active subscription).

Supported event types:
- subscription.activated
- subscription.expired
- subscription.cancelled
- plan.synced

Communication protocol: One-way HTTP POST from SaaS to Core.
No response callbacks from Core to SaaS.

2. ENDPOINT SPECIFICATION
============================================================

Method:     POST
Full path:  /api/internal/core/sync/
Content-Type: application/json

Authentication: HMAC-SHA256 (see Section 3)
CSRF: EXEMPT (decorator applied to this endpoint only)
      All other endpoints retain Django CSRF protection.

Required headers:
  Content-Type:        application/json
  X-Menuno-Event-Id:   UUID (v4) - unique per request
  X-Menuno-Timestamp:  ISO-8601 datetime string
  X-Menuno-Signature:  HMAC-SHA256 hex digest

Success status codes:
  201 CREATED   - new resource created
  200 OK        - existing resource updated or duplicate event

Response format:
  {
    "message": "CREATED" | "OK",
    "status": 201 | 200,
    "result": { ... }
  }


============================================================
3. HMAC AUTHENTICATION
============================================================

Algorithm:
  HMAC-SHA256(MENUNO_CORE_SYNC_SECRET, message)

Message construction (exactly as implemented in Core):
  message = timestamp_string + "." + raw_body_bytes

Where:
  timestamp_string = value of X-Menuno-Timestamp header (UTF-8 string)
  raw_body_bytes   = the exact bytes of the HTTP request body

Concrete implementation (Python):
  message = (timestamp + ".").encode("utf-8") + raw_body
  expected = hmac.new(
      secret.encode("utf-8"),
      message,
      hashlib.sha256,
  ).hexdigest()

The SaaS must compute the signature identically.

Signature encoding: lowercase hexadecimal (64 characters)
Comparison: constant-time via hmac.compare_digest()


--- Headers in detail ---

X-Menuno-Event-Id
  Type: UUID (v4 format)
  Example: fdf7de65-06cd-4536-ba60-f1e736f522d8
  Required: YES
  Purpose: Idempotency - duplicate event IDs are safely ignored.
  Must be unique per business event. Same event_id = same result.

X-Menuno-Timestamp
  Type: ISO-8601 datetime string
  Format: YYYY-MM-DDTHH:MM:SS.ffffff+HH:MM (or with Z suffix)
  Example: 2026-08-16T16:18:01.265961+00:00
  Required: YES
  Purpose: Replay attack prevention.
  Tolerance: 300 seconds (5 minutes) drift from Core server time.
  Core uses Django timezone.now() for comparison (timezone-aware).
  Timestamps older than 5 minutes are rejected with 401.

X-Menuno-Signature
  Type: Hex string (64 characters)
  Example: c86ec86f4ff72d8967978b69ea54f4d7d1ad366a6474608327f59a478c9f5595
  Required: YES
  Purpose: Proves the request came from someone who knows the shared secret.
  Computed over: timestamp + "." + raw_body (as described above)

--- Security notes ---

- The raw request body bytes are used for signature verification.
  The SaaS must sign the exact bytes it sends.
  If using Python requests: sign(request.content), not request.text.

- The secret MUST be identical on both SaaS and Core.
  Never hardcode it. Use environment variables.

- The secret MUST NOT be logged, transmitted in responses,
  or included in version control.

4. REQUEST JSON SCHEMA
============================================================

The Core endpoint accepts two payload shapes depending on event_type.

--- Schema A: Subscription event ---

{
  "event_id":       "<UUID string, required>",
  "event_type":     "<string, required>",
  "subscription_id": "<UUID string, required>",
  "cafe_id":        "<UUID string, required>",
  "plan":           "<object, required>",
  "status":         "<string, required>",
  "started_at":     "<ISO-8601 string or null, optional>",
  "expires_at":     "<ISO-8601 string or null, optional>",
  "version":        "<integer, optional, default=1>",
  "occurred_at":    "<ISO-8601 string, required>"
}

Field details:

  event_id (UUID, required)
    Unique event identifier for idempotency.
    Same event_id sent twice = second request is a no-op.
    Generated by SaaS per business event.

  event_type (string, required)
    Must be one of:
      "subscription.activated"
      "subscription.expired"
      "subscription.cancelled"
    Unknown values return 400.

  subscription_id (UUID, required)
    The stable cross-system identifier for this subscription.
    Must match across all sync events for the same subscription.
    Core stores this as Subscription.external_id (UUIDField, unique).

  cafe_id (UUID, required)
    The cafe's external_id (UUID) as created in Core.
    Core looks up CafeInfo via: CafeInfo.objects.get(cafe__external_id=cafe_id)
    If cafe is not found, returns 400.

  plan (object, required)
    Complete plan data. Core syncs this first before syncing the subscription.
    See "Plan Object" below for required fields.

  status (string, required)
    Must be one of: "PENDING", "ACTIVE", "EXPIRED", "CANCELLED"
    Core derives is_active from this: is_active = (status == "ACTIVE")

  started_at (ISO-8601 string or null, optional)
    When the subscription started.
    If null, Core leaves existing value unchanged on update.

  expires_at (ISO-8601 string or null, optional)
    When the subscription expires.
    If null, Core leaves existing value unchanged on update.

  version (integer, optional, default=1)
    Used for stale event prevention.
    Core only updates if incoming_version >= current_version.
    If incoming_version < current_version, the event is silently ignored.

  occurred_at (ISO-8601 string, required)
    When the event occurred in SaaS.
    Used for logging. Not used for staleness check.


--- Schema B: Plan event ---

{
  "event_id":    "<UUID string, required>",
  "event_type":  "plan.synced",
  "plan":        "<object, required>",
  "occurred_at": "<ISO-8601 string, required>"
}

This syncs only a plan without a subscription.
Used when a plan is created or updated in SaaS.


--- Plan Object (required fields) ---

{
  "external_id":    "<UUID string, required>",
  "slug":           "<string, required>",
  "title":          "<string, required>",
  "price":          "<integer, required>",
  "duration_days":  "<integer, required>",
  "max_products":   "<integer, optional, default=100>",
  "is_active":      "<boolean, optional, default=true>",
  "version":        "<integer, optional, default=1>"
}

Field details:

  external_id (UUID, required)
    Stable cross-system identifier for this plan.
    Core stores this as Plan.external_id (UUIDField, unique).
    Must be the same UUID across all sync events for the same plan.

  slug (string, required)
    URL-safe identifier. Core stores as SlugField (unique=True).
    Example: "professional", "starter-monthly"

  title (string, required)
    Human-readable plan name.
    Example: "Professional", "Starter Monthly"

  price (integer, required)
    Plan price in Rials (IRR).
    NOT in Toman. See Section 9.
    Example: 500000 means 500,000 Rials.

  duration_days (integer, required)
    Number of days the plan is valid.
    Example: 30 for monthly, 365 for yearly.

  max_products (integer, optional, default=100)
    Maximum number of products allowed under this plan.

  is_active (boolean, optional, default=true)
    Whether the plan is currently active.

  version (integer, optional, default=1)
    Used for staleness prevention on plan updates.

5. CAFE IDENTIFICATION
============================================================

Core identifies the cafe using cafe_id (UUID).

Lookup path in Core:
  CafeInfo.objects.select_related("cafe").get(
      cafe__external_id=cafe_external_id
  )

This means:
  cafe_id in the request = Cafe.external_id (UUIDField)

The cafe MUST already exist in Core before a subscription sync.
Cafes are created via a separate endpoint (POST /api/internal/integration/cafes/)
using X-Internal-API-Key authentication.

If cafe_id does not match any Cafe in Core:
  Core returns 400: "Cafe with external_id {id} not found in Core"


============================================================
6. PLAN IDENTIFICATION
============================================================

Core identifies the plan using plan.external_id (UUIDField, unique=True).

Plan sync happens BEFORE subscription sync within the same request.
Core calls PlanSyncService.sync_plan(plan_data) first.

Plan behavior:
  - If plan with external_id exists: update fields (if version >= current)
  - If plan with external_id does not exist: create new plan
  - If incoming version < current version: silently ignore (no update)

The plan MUST be included in every subscription sync request.
The plan data in the subscription request is the source of truth.


============================================================
7. SUBSCRIPTION ACTIVATION
============================================================

After HMAC verification, timestamp check, and event_id check:

1. Cafe lookup by cafe_id (external_id UUID)
2. Plan sync (create or update plan from plan data)
3. Event idempotency check:
   - If event_id already exists in SyncEvent table:
     Return existing subscription, status 200/201 (no changes made)
4. Subscription sync:
   - If subscription with external_id exists:
     Update if incoming_version >= current_version
     Fields updated: status, plan, started_at, expires_at, is_active, version
   - If subscription does not exist:
     Create new subscription with all provided fields

is_active derivation:
  is_active = (status == "ACTIVE")
  This is computed by Core, not sent by SaaS.

Legacy fields:
  start_date and end_date are derived from started_at and expires_at.
  start_date = started_at.date()
  end_date = expires_at.date()

Plan assignment:
  Subscription.plan = the Plan synced from plan data in same request.
  Plan is looked up by external_id after sync.

Cafe assignment:
  Subscription.cafe = the CafeInfo found via cafe_id.
  Subscription is linked to CafeInfo (OneToOne), not Cafe directly.


============================================================
8. IDEMPOTENCY
============================================================

Event tracking table: SyncEvent
  event_id: UUIDField (unique=True, db_index=True)
  event_type: CharField(max_length=100)
  subscription_external_id: UUIDField (nullable)
  status: CharField ("PROCESSED" or "FAILED")
  payload_hash: CharField (SHA-256 of str(payload))
  created_at: from BaseModel

Behavior:
  1. Core attempts to INSERT a SyncEvent with the given event_id.
  2. If the INSERT succeeds: event is new, process normally.
  3. If the INSERT fails (IntegrityError due to unique constraint):
     event is a duplicate, skip processing, return existing subscription.

Duplicate response:
  Core returns the existing subscription data with status 200 or 201.
  The response is identical to a first-time request.
  No error is returned for duplicate events.

SaaS should ALWAYS use a unique event_id per business event.
Examples of unique events:
  - Payment success for subscription X
  - Subscription X expired
  - Subscription X cancelled
  - Plan Y updated

SaaS should NOT reuse event_ids across different events.


============================================================
9. AMOUNT AND CURRENCY
============================================================

Plan.price is stored as PositiveIntegerField.

The price is in RIALS (IRR), NOT in Toman.

Examples:
  500000  = 500,000 Rials = 50,000 Toman
  1000000 = 1,000,000 Rials = 100,000 Toman

Core does NOT handle currency conversion.
Core does NOT validate currency.
Core stores the raw integer value sent by SaaS.

SaaS must send the price in Rials when syncing a plan.

10. ERROR RESPONSES
============================================================

All responses follow this format:
  {
    "message": "<string>",
    "status": <integer>,
    "result": <object or string>
  }


--- 400 BAD REQUEST ---

Returned for:
  - Unknown event_type
  - Missing required fields in payload
  - Invalid plan data (missing external_id, slug, etc.)
  - Invalid status value (not in PENDING/ACTIVE/EXPIRED/CANCELLED)
  - Cafe with given external_id not found in Core
  - Missing or malformed JSON body

Example:
  {
    "message": "ERROR",
    "status": 400,
    "result": {"error": "Cafe with external_id abc-123 not found in Core"}
  }


--- 401 UNAUTHORIZED ---

Returned for:
  - Missing X-Menuno-Signature header
  - Missing X-Menuno-Timestamp header
  - Missing X-Menuno-Event-Id header
  - Invalid HMAC signature (secret mismatch or wrong body)
  - Timestamp older than 300 seconds (5 minutes)
  - Empty request body
  - Invalid timestamp format (not ISO-8601)

Example (invalid signature):
  {
    "detail": "Invalid HMAC signature."
  }


--- 403 FORBIDDEN ---

This status is NOT returned by the CoreSyncAPIView itself.
If you receive 403, it means CSRF middleware blocked the request.
This indicates the request did not reach the view.
Check that you are sending to /api/internal/core/sync/ (not a different path)
and that CSRF cookie is not interfering.


--- 404 NOT FOUND ---

This status is NOT returned by the sync endpoint.
If you receive 404, the URL path is incorrect.
The correct path is: /api/internal/core/sync/


--- 409 CONFLICT ---

Not implemented. Duplicate events are handled via idempotency (200/201).


--- 422 UNPROCESSABLE ENTITY ---

Not implemented. Validation errors return 400.


--- 500 INTERNAL SERVER ERROR ---

Returned for unexpected server-side errors.
SaaS should retry on 500.

Example:
  {
    "message": "ERROR",
    "status": 500,
    "result": "Internal sync error"
  }


============================================================
11. RETRY BEHAVIOR
============================================================

What to retry:
  - 500 Internal Server Error (server-side failure)
  - Connection timeout
  - Connection refused
  - Network errors

What NOT to retry:
  - 400 Bad Request (fix the payload first)
  - 401 Unauthorized (fix authentication first)
  - 403 Forbidden (check URL path and CSRF)
  - 404 Not Found (check URL path)

Retry strategy (recommended):
  - Maximum 3 retries
  - Exponential backoff: 1s, 2s, 4s
  - Do NOT retry on 4xx errors
  - Do NOT roll back payment/order on sync failure

Idempotency safety:
  Retrying the same request with the same event_id is safe.
  Core will detect the duplicate and return the existing result.
  No side effects on retry.

Payment-safe design:
  Core sync is called AFTER payment/order transaction commits.
  If Core sync fails:
    - Do NOT roll back the payment
    - Do NOT mark payment as failed
    - Do NOT mark order as failed
    - Log the failure and retry later


============================================================
12. SECURITY REQUIREMENTS
============================================================

HMAC Authentication:
  - SaaS and Core share MENUNO_CORE_SYNC_SECRET
  - Signature is HMAC-SHA256(secret, timestamp + "." + raw_body)
  - Constant-time comparison prevents timing attacks
  - Signature is computed over raw body bytes, not parsed JSON

Timestamp Validation:
  - Must be within 300 seconds (5 minutes) of Core server time
  - Prevents replay attacks: captured requests expire
  - SaaS clock must be reasonably synchronized (NTP recommended)

Replay Protection:
  - Same event_id submitted twice = second request is a no-op
  - SyncEvent table tracks all processed events
  - No duplicate subscriptions or plans are created

CSRF Behavior:
  - CoreSyncAPIView is CSRF-exempt via @method_decorator(csrf_exempt)
  - All other Core endpoints retain CSRF protection
  - SaaS must NOT include CSRF cookies in requests

Raw Request Body:
  - HMAC signature is computed over the exact bytes sent
  - SaaS must sign request.content, not request.text
  - JSON serialization differences (whitespace, key order) will break the signature

Secret Handling:
  - MENUNO_CORE_SYNC_SECRET must be identical on SaaS and Core
  - Must be stored in environment variables, not in code
  - Must NOT be logged in application logs
  - Must NOT be included in error messages or responses
  - Rotate the secret periodically; during rotation, support both old and new

Logging Restrictions:
  - Do NOT log MENUNO_CORE_SYNC_SECRET
  - Do NOT log the raw HMAC signature
  - Safe to log: event_id, event_type, timestamp, status code

15. COMPLETE REQUEST EXAMPLE (curl)
============================================================

Note: This example uses a placeholder secret. Replace with actual shared secret.

Step 1: Generate a UUID for event_id
  event_id="fdf7de65-06cd-4536-ba60-f1e736f522d8"

Step 2: Generate ISO-8601 timestamp
  timestamp="2026-08-16T16:18:01.265961+00:00"

Step 3: Build the JSON body
  body='{"event_id":"fdf7de65-06cd-4536-ba60-f1e736f522d8","event_type":"subscription.activated","subscription_id":"a1b2c3d4-e5f6-7890-abcd-ef1234567890","cafe_id":"11111111-2222-3333-4444-555555555555","plan":{"external_id":"99999999-8888-7777-6666-555555555555","slug":"professional","title":"Professional","price":500000,"duration_days":30},"status":"ACTIVE","started_at":"2026-08-16T16:18:01+00:00","expires_at":"2026-09-15T16:18:01+00:00","version":1,"occurred_at":"2026-08-16T16:18:01+00:00"}'

Step 4: Compute the HMAC signature

  Python:
    import hmac, hashlib
    secret = "YOUR_SECRET_HERE"  # Replace with actual secret
    message = (timestamp + ".").encode("utf-8") + body.encode("utf-8")
    signature = hmac.new(
        secret.encode("utf-8"),
        message,
        hashlib.sha256,
    ).hexdigest()

  Bash:
    secret="YOUR_SECRET_HERE"
    timestamp="2026-08-16T16:18:01.265961+00:00"
    body='{"event_id":"fdf7de65-06cd-4536-ba60-f1e736f522d8",...}'
    signature=$(echo -n "${timestamp}.${body}" | openssl dgst -sha256 -hmac "$secret" | awk '{print $2}')

Step 5: Send the request

  curl -X POST \
    http://127.0.0.1:8002/api/internal/core/sync/ \
    -H "Content-Type: application/json" \
    -H "X-Menuno-Event-Id: fdf7de65-06cd-4536-ba60-f1e736f522d8" \
    -H "X-Menuno-Timestamp: 2026-08-16T16:18:01.265961+00:00" \
    -H "X-Menuno-Signature: COMPUTED_SIGNATURE_HERE" \
    -d '{"event_id":"fdf7de65-06cd-4536-ba60-f1e736f522d8","event_type":"subscription.activated","subscription_id":"a1b2c3d4-e5f6-7890-abcd-ef1234567890","cafe_id":"11111111-2222-3333-4444-555555555555","plan":{"external_id":"99999999-8888-7777-6666-555555555555","slug":"professional","title":"Professional","price":500000,"duration_days":30},"status":"ACTIVE","started_at":"2026-08-16T16:18:01+00:00","expires_at":"2026-09-15T16:18:01+00:00","version":1,"occurred_at":"2026-08-16T16:18:01+00:00"}'

IMPORTANT NOTES FOR CURL:
  - The -d flag sends the body as-is. Do not reformat the JSON.
  - The signature must be computed over the EXACT bytes sent by curl.
  - Do NOT include a CSRF cookie.
  - Do NOT include an Authorization header.
